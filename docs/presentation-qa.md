# 발표 예상 질문 및 답변 — 홈쇼퍼(HomeShopper)

> 경기도 공공데이터 및 AI 활용 경진대회 발표 대비용 Q&A 정리
> 작성 기준: 현재 저장소(Home_prototype) 코드/문서 상태 (2026-07-26)

---

## 1. 서비스/아이템 관련

### Q1. 이 서비스가 해결하려는 문제는 무엇인가요?
전월세 매물 계약 전 확인해야 할 서류(등기부등본, 건축물대장, 실거래가 등)를
일반인이 직접 확인하기 어렵고, 허위매물·근저당·위반건축물 같은 위험 신호를
놓친 채 계약해 피해를 보는 경우가 많습니다. 홈쇼퍼는 다방 매물 링크 하나만
입력하면 이런 위험 신호를 자동으로 대조해 신호등 색(정상/주의/위험)으로
정리한 리포트를 제공합니다.

### Q2. 서비스 이용 흐름이 어떻게 되나요?
1. 사용자가 다방(부동산 플랫폼) 매물 링크를 랜딩 페이지 검색창에 붙여넣음
2. `/analyze` 페이지에서 분석 요청(`POST /analyses`) 후 대기
3. 완료되면 `/report/[id]`에서 리포트 확인 — 실거래가 비교, 건축물대장 요약,
   중개업소 등록 유효성 등을 신호등 형태로 확인
4. 더 상세한 확인(동·호수 특정 등기부 분석)이 필요하면 카카오 로그인 후
   프리미엄 요청(`premium-requests`) 또는 전문가 동행 임장 사전예약
   (`reservations`)으로 이어짐

### Q3. 왜 "다방 링크"만 지원하나요? 다른 플랫폼(직방 등)은요?
현재는 프리토타입 단계로 실제 수요 검증이 목적이라 단일 플랫폼(다방)으로
범위를 좁혔습니다. `lib/listing-input.ts`에서 입력값이 다방 매물 링크인지
분류(`classifyListingInput`)하고, 아니면 에러 메시지를 보여줍니다. 확장은
이 분류 로직에 플랫폼 패턴을 추가하는 방식으로 가능합니다.

### Q4. 비즈니스 모델은 무엇인가요?
"반값 수수료" — 기존 부동산 중개 수수료 대비 절반 가격에 매물 검증부터
계약, 입주 후 하자보수/갈등 조정까지 전 생애주기를 대행합니다. 현재는 매물
검증(무료 기본 리포트 + 유료 프리미엄)과 동행 임장·정찰 중개를 사전예약
받는 단계입니다.

### Q5. 지금까지의 검증 성과나 수상 이력이 있나요?
랜딩 페이지에 노출된 대로 "하나 소셜벤처 유니버시티 선정"과 "경기도
공공데이터 활용 창업경진대회 수상" 이력이 있습니다. 현재 이 저장소 자체는
그 다음 단계의 프리토타입(실제 서비스 검증용 최소 기능 제품)입니다.

## 2. 공공데이터 활용 관련

### Q6. 어떤 공공데이터를 활용하나요?
- **등기부등본**: 소유자 일치 여부, 근저당·가압류 등 권리관계, 최우선변제금
  (`RegistryFacts`: `ownerMatchesLandlord`, `maxClaimAmount`,
  `priorLienSummary`, `priorDepositInfo`)
- **건축물대장**: 주용도, 사용승인연도, 위반건축물 여부
  (`ReportFacts.buildingRegistry`)
- **국토교통부 실거래가 데이터**: 인근 동일 조건 거래 사례를 모아 적정
  시세 범위 산출 (`ReportFacts.recentTransactions` — 거래 건수, 가격
  범위, 보정 평균)
- **공인중개사 등록정보**: 매물을 올린 중개업소의 등록 상태 유효성 확인
  (`ReportFacts.agencyValidity`)

### Q7. 공공데이터를 어떻게 "가공"해서 가치를 만드나요?
단순 원본 데이터 나열이 아니라, 사용자가 입력한 매물 정보(주소, 보증금,
계약 형태)를 기준으로 여러 공공데이터 소스를 **교차 대조**합니다. 예를 들어
매물 광고가와 인근 실거래가 평균을 비교해 이상치를 잡아내고, 건축물대장상
위반건축물 여부·등기부의 근저당 설정액을 보증금과 비교해 "이 계약이
안전한가"라는 하나의 판단으로 압축해 신호등 색으로 보여줍니다. 이 매칭·판단
로직은 별도의 Python 분석 서버(백엔드)에서 수행되고, 프론트엔드는 그 결과를
소비·표현하는 역할입니다.

### Q8. 데이터 최신성/신뢰성은 어떻게 보장하나요?
`apiStatus` 필드로 각 데이터 소스(실거래가/등기부/중개업소)별 조회
성공·실패·대기 상태를 개별 추적합니다. 한 소스가 실패해도 나머지 정보는
정상 노출되는 부분 성공(`status: 'partial'`) 구조입니다. 예를 들어
건축물대장에서 위반건축물 여부(`hasViolation`)를 확인할 수 없으면 "안전"이
아니라 명시적으로 "확인 불가"로 표시합니다 — 데이터 부재를 안전 신호로
오인시키지 않기 위한 설계입니다.

### Q9. 개인정보(주소 등)는 어떻게 보호하나요?
리포트에는 정확한 지번 대신 마스킹된 주소(`addressMasked`, 예:
"서울 마포구 연남동 21번지 인근")만 노출됩니다. 정확한 동·호수 같은
세부 정보는 로그인 후 프리미엄 요청 시에만 별도로 입력받고(30자 제한),
관리자 화면도 조회 전용이며 로그인(카카오 OAuth, AGENT 권한) 없이는
접근할 수 없습니다.

## 3. AI/기술 활용 관련

### Q10. AI는 구체적으로 어디에 쓰이나요?
매물 링크에서 주소·거래조건을 추출하고, 여러 공공데이터를 대조해 위험
신호(`concerns`)를 판단하는 분석 로직이 백엔드(Python 분석 서버)에
있습니다. 이 저장소(프론트엔드)는 그 분석 결과를 사용자에게 보여주는
계층이라, AI/규칙 기반 판단 로직 자체는 백엔드 저장소에 있습니다.
(발표 시 백엔드 저장소의 판단 로직 코드/모델을 별도로 준비해 설명하는 것을
권장합니다.)

### Q11. 프론트엔드는 어떤 기술 스택으로 만들었나요?
- **Next.js 16** (App Router, `app/` 디렉토리 기반) + **React 19**
- **TypeScript** — API 응답 타입을 `lib/types.ts`에 엄격히 정의해 null
  가능성까지 명시(예: 건축물대장 없음, 위반 여부 확인 불가 등 실제 API의
  불완전성을 타입으로 표현)
- **Tailwind CSS v4** — 유틸리티 기반 스타일링
- **motion(Framer Motion 계열)** — 스크롤 연동 애니메이션(히어로 섹션 pull
  효과), 단계별 reveal 애니메이션
- **Vitest + Testing Library** — 유닛/컴포넌트 테스트
- **ESLint** — 코드 품질 검사

### Q12. 프론트/백엔드는 어떻게 나뉘어 있고 왜 분리했나요?
프론트엔드(Next.js, 이 저장소)와 백엔드(FastAPI 계열로 추정, EC2에 별도
배포)를 분리했습니다. 분석 로직(공공데이터 조회·대조·판단)은 무겁고 외부
API 의존성이 크기 때문에 별도 서버로 두고, 프론트는 `NEXT_PUBLIC_API_BASE_URL`
환경변수로 백엔드 주소를 주입받아 REST API(`/api/v1/...`)로 통신합니다.
이렇게 하면 분석 로직 변경이 프론트 배포와 독립적으로 이루어질 수 있고,
프론트는 화면/UX에 집중할 수 있습니다.

### Q13. 로그인/인증은 어떻게 처리하나요?
카카오 OAuth를 사용합니다(`lib/oauth.ts`). 무료 기본 리포트는 로그인 없이
누구나 볼 수 있고, 프리미엄 요청·사전예약처럼 개인정보(연락처, 동·호수)가
필요한 액션에서만 로그인을 요구하는 구조로, 진입장벽을 최소화했습니다.

### Q14. 테스트는 어떻게 하고 있나요?
Vitest 기반 유닛 테스트가 있고(`tests/` 디렉토리, 예:
`tests/lib/analytics.test.ts`), 분석 이벤트 전송(`lib/analytics.ts`) 같은
핵심 유틸 로직을 검증합니다. UI 컴포넌트는 실제 개발 서버로 브라우저에서
직접 확인하는 방식을 병행합니다.

### Q15. 왜 App Router(Next.js 16)를 선택했나요?
서버 컴포넌트 기반으로 초기 로딩을 최적화하고, 파일 기반 라우팅으로
`/analyze`, `/report/[id]`, `/reserve`, `/admin/*` 같은 페이지 구조를
직관적으로 관리할 수 있기 때문입니다. 다만 이 프로젝트는 Next.js의 최신
버전(16)이라 일부 API가 기존 학습 자료와 달라, 저장소 내
`node_modules/next/dist/docs/`의 최신 문서를 직접 참고하며 개발했습니다
(`AGENTS.md` 참고).

## 4. 개발 과정/의사결정 관련

### Q16. 개발하면서 겪은 가장 큰 이슈는 무엇이었나요?
배포 주소 불일치 이슈가 있었습니다. 백엔드 CORS·카카오 리다이렉트가 허용한
Vercel 주소(`pretotype`)와 실제 배포 주소(`prototype`)가 철자 한 글자
차이로 서로 다른 프로젝트였고, 이 때문에 실제 배포본에서 API가 403으로
막히는 문제를 발견했습니다(`API_INTEGRATION_STATUS.md` 참고). 이런 크로스팀
연동 이슈는 프론트 코드만으로는 못 잡고, 실제 배포 환경에서의 curl/CORS
테스트로 확인했습니다.

### Q17. 로컬 개발 중 API 연동을 어떻게 검증했나요?
백엔드가 Vercel 운영 도메인만 CORS 허용하기 때문에 로컬(`localhost:3000`)
에서는 실제 API 응답을 브라우저에서 받을 수 없습니다. 대신 각 화면이 API
실패 시 정상적으로 에러 UI로 폴백하는지를 검증하고, 실제 성공 경로는
Vercel 배포 환경에서 확인하는 전략을 취했습니다.

### Q18. 없는 리포트나 잘못된 요청은 어떻게 처리하나요?
백엔드가 없는 리포트 조회 시 404가 아니라 400을 반환하는 등 문서와 실제
동작이 다른 부분이 있어, 프론트에서는 400과 404를 모두 "리포트 없음"으로
동일하게 처리하도록 방어적으로 구현했습니다.

### Q19. 왜 랜딩 페이지 히어로에 실제 리포트 컴포넌트를 그대로 재사용했나요?
`SampleReport`가 실제 리포트 페이지와 동일한 `ReportSummary` 컴포넌트에
샘플 데이터(`demoReport`)를 넣어 렌더링합니다. 목업 이미지를 따로 만들면
실제 서비스 화면과 점점 달라지는 문제가 생기므로, 랜딩과 실제 리포트가
항상 같은 컴포넌트를 공유하도록 설계했습니다.

### Q20. 접근성이나 사용자 경험 측면에서 신경 쓴 부분은?
- 검색창에 `aria-label`, 에러 메시지에 `role="alert"` 부여
- `prefers-reduced-motion` 감지 후 애니메이션 최소화(모션 민감 사용자 배려)
- 위반건축물처럼 데이터가 없는 항목은 "안전"이 아닌 "확인 불가"로 명확히
  구분 표시해 오인을 방지

## 5. 향후 계획/한계 관련

### Q21. 아직 미완성이거나 제한적인 부분은?
- 관리자 화면은 조회 전용(쓰기/발행 기능 없음)
- 공유(share)·대기신청(waitlist) 기능은 의도적으로 아직 백엔드 연동 보류
- 사용자 행동 로그(클릭/방문 이벤트)를 조회하는 API가 백엔드에 아직 없어,
  관리자 "로그" 화면은 예약 데이터를 대신 기준으로 구성
- 현재 다방 매물 링크만 지원(타 플랫폼 미지원)

### Q22. 앞으로 어떤 기능을 추가할 계획인가요?
랜딩 페이지의 "COMING SOON" 섹션에 나온 대로 전문가 동행 임장과 정찰제
반값 중개가 다음 단계입니다. 현재는 사전예약(`/reserve`)만 받고 있고,
실제 매칭·중개 워크플로우는 이후 개발 범위입니다.

### Q23. 확장 시 다른 지역/다른 매물 플랫폼도 지원 가능한가요?
가능합니다. 매물 입력 분류 로직(`classifyListingInput`)과 백엔드 분석
파이프라인이 플랫폼별로 매물 정보를 파싱하는 어댑터를 추가하면 되는
구조라, 프론트엔드 리포트 UI(신호등 형식)는 플랫폼에 무관하게 재사용
가능합니다.

## 6. UI/UX 비평적 질문 (Critical UI/UX)

### Q24. 분석 로딩 화면의 진행 애니메이션이 실제 진행률을 반영하나요?
아니요. `ProgressAnimation`(`components/analyze/ProgressAnimation.tsx`)은
실제 분석 단계와 무관하게 도형이 회전·변형하는 무한 루프 애니메이션이고,
`/analyze` 페이지에서는 `durationMs`(기본 3000ms) 고정 타이머가 끝나면
`onComplete`를 호출해 넘어가는 방식입니다. 즉 "몇 % 완료"가 아니라 정해진
시간 동안 로딩처럼 보이게 만든 연출입니다. 실제 API 응답이 3초보다 오래
걸리면 사용자는 이미 끝난 줄 알았던 애니메이션이 계속 반복되는 걸 보게
되고, 반대로 실제 응답이 그보다 훨씬 빨리 와도 최소 3초는 기다리게
설계되어 있진 않은지(또는 반대로 실제 응답 완료 전에 타이머가 끝나
빈 화면으로 넘어가진 않는지) 짚어볼 지점입니다. → 실제로는 실제 API 호출이
끝나는 시점(`then`/`catch`)에 맞춰 상태를 전환하는 코드와, 이 타이머 기반
연출이 화면별로 다르게 쓰이고 있어 일관성 검증이 필요합니다.

### Q25. 왜 모든 페이지/컴포넌트가 `'use client'`인가요? Next.js 16 App
Router의 서버 컴포넌트는 활용하지 않았나요?
맞습니다. 랜딩 페이지, 리포트 페이지, analyze 페이지 등 핵심 화면 대부분이
`'use client'`로 시작합니다. 스크롤 연동 모션(`useScroll`, `useTransform`),
로컬 상태(폼 입력, 로딩 상태) 의존도가 높아 클라이언트 컴포넌트가
불가피한 부분도 있지만, 그 대가로 서버 컴포넌트가 주는 초기 페이로드
축소·서버 사이드 데이터 페칭 이점은 거의 활용하지 못하고 있습니다. 예를
들어 리포트 페이지의 정적 마크업(제목, 안내문 등)까지 클라이언트에서
렌더링됩니다. 이는 "왜 App Router를 썼는가"라는 질문에 대한 약점이 될 수
있어, 개선 방향으로 정적 셸(shell)만 서버 컴포넌트로 분리하는 안을 준비해두면
좋습니다.

### Q26. `Suspense` fallback과 실제 로딩 상태가 동일한 이유가 뭔가요? 중복
아닌가요?
`app/report/[id]/page.tsx`의 `ReportPage`는 `useSearchParams`가 요구하는
`Suspense` 경계의 fallback으로 `ReportContent`의 `'loading'` 상태와
동일한 `ReportShell + ProgressAnimation`을 다시 그립니다. 코드는 중복돼
보이지만 의도적입니다 — fallback을 비워두면 서버가 배경/로더 없이 빈
화면을 그렸다가 클라이언트 번들이 붙는 순간 배경과 콘텐츠가 순차적으로
"툭툭" 나타나는 현상이 있었기 때문입니다. 다만 두 곳의 마크업이 물리적으로
분리되어 있어, 한쪽만 수정하고 다른 쪽을 놓치면 다시 그 깜빡임이
재발할 수 있는 구조적 약점은 남아 있습니다(공유 컴포넌트로 추출하지 않은
이유를 질문받을 수 있음 — 실제로는 `ReportShell`이라는 이름으로 이미 부분
추출은 되어 있으나, `Suspense fallback`과 `ReportContent` 내부 두 곳에서
각각 호출).

### Q27. 글래스모피즘(반투명 블러 카드) 스타일을 선택한 이유는? 성능/가독성
트레이드오프는 고려했나요?
리포트 카드들이 `backdrop-blur-xl`, `rgba(255,255,255,0.55)` 반투명
배경, `glass-edge`/`shadow-glass` 등 글래스모피즘 스타일을 씁니다. 신뢰감
있는 "문서" 느낌과 배경 그라디언트(`ReportBackdrop`)를 살리기 위한
선택이지만, `backdrop-filter: blur`는 저사양 기기·구형 브라우저에서 렌더링
비용이 크고, 밝은 배경 위 얇은 텍스트의 명암비(contrast)가 낮아질 위험이
있습니다. 실제로 접근성(WCAG 명암비) 기준으로 텍스트 색상을 검증했는지,
저사양 기기에서의 프레임 드랍을 테스트했는지는 비판적으로 점검할 부분입니다.

### Q28. 스크롤 연동 히어로 "pull" 애니메이션이 모든 디바이스/브라우저에서
안정적인가요?
`app/page.tsx`의 히어로는 `useScroll`/`useTransform`으로 스크롤 위치에 따라
opacity·scale·y를 실시간 계산하고, `getBoundingClientRect`/`offsetTop`
기반 측정을 코드 주석에서 스스로 "이전엔 계속 값이 어긋났다"고 명시할
정도로 레이아웃 변화에 취약했던 이력이 있습니다. 현재는 히어로 높이가
뷰포트보다 크면(`fits` 체크) 아예 pin 효과를 끄는 폴백을 두었지만, 폰트
로딩 지연이나 동적 콘텐츠 높이 변화처럼 `ResizeObserver`가 아닌
`resize` 이벤트만으로 못 잡는 케이스는 여전히 남아 있을 수 있습니다 —
이런 "측정 기반" 애니메이션의 구조적 리스크를 인지하고 있는지가
비평 포인트입니다.

### Q29. 랜딩 히어로가 실제 리포트 컴포넌트를 그대로 재사용한다고 했는데,
이게 오히려 사용자에게 혼란을 줄 수 있지 않나요?
`SampleReport`가 실제 서비스 화면과 동일한 컴포넌트·데이터 구조를 쓰는
장점은 있지만, 화면 하단에 "※ 예시 화면입니다. 실제 매물 정보가 아닙니다"
라는 작은 캡션 하나로만 이를 구분하고 있습니다. 첫 방문자가 이 문구를
놓치면 실제 검증된 매물 정보로 착각할 위험이 있어, 시각적 구분(워터마크,
블러 처리, 배지 등)이 문구보다 더 강한 신호를 줄 수 있는지 검토가
필요합니다.

### Q30. 에러/실패 상태 디자인에 일관성이 있나요? (400/404/500, 부분 실패
등 케이스가 여러 개인데)
리포트 조회 실패는 `notFound`/`error` 두 상태로 단순화(400·404는
notFound로 통합)했지만, 리포트 **내부**의 개별 데이터 실패는
`apiStatus`(각 섹션별 ok/failed/pending)로 훨씬 세분화되어 있습니다. 즉
"리포트 자체를 못 찾음"과 "리포트는 있지만 일부 데이터 섹션만 실패"가
서로 다른 두 체계로 표현되는데, 사용자 입장에서 이 두 실패 유형이 화면
톤(카피, 색상, 아이콘)에서 얼마나 일관되게 구분되는지, 실제 리포트
카드에서 "확인 불가" 표시가 충분히 눈에 띄는지는 실사용 테스트로
검증이 필요한 부분입니다.

### Q31. 라우트 파라미터(리포트 ID)를 다루면서 보안 이슈를 겪었다고
들었는데, UI 관점에서는 어떻게 드러났나요?
`/report/7%2F..%2F..%2Fadmin%2Fpremium-requests`처럼 조작된 URL을 넣으면
디코딩된 `id`가 이스케이프 없이 API 경로 문자열에 그대로 삽입되어, 실제
요청이 `/api/v1/admin/premium-requests`로 완전히 다른 엔드포인트로
새어나가는 문제가 있었습니다(`SECURITY_NOTES.md` §2). 지금은
`encodeURIComponent(id)`로 고쳤지만, 이는 "화면에 이상하게 보인다" 같은
증상이 아니라 **정상적으로 보이는 화면 뒤에서 완전히 다른 API가
호출되는** 조용한 실패였다는 점에서, UI 테스트만으로는 못 잡는 유형의
버그였다는 걸 짚을 수 있습니다.

### Q32. 폼(예약, 프리미엄 요청)에서 사용자 입력 실패를 어떻게 처리하나요?
전부 API 응답을 신뢰하고 그대로 화면에 반영하나요?
아닙니다. `SECURITY_NOTES.md` §1에 기록된 사례처럼, 예약 성공
응답(`201`)에 `queueNumber` 필드가 없으면 과거에는 URL에 문자 그대로
`"undefined"`가 박혀 "예약 순번 #undefined"라는, 마치 진짜 값처럼 보이는
깨진 화면이 노출된 적이 있습니다. 지금은 값이 있을 때만 조건부로 쿼리에
붙이도록 고쳤지만, 이는 "백엔드가 201을 주면 성공"이라는 가정만으로는
프론트 화면의 무결성을 보장할 수 없다는 사례로, API 계약(contract)을
프론트가 얼마나 방어적으로 검증해야 하는지에 대한 질문으로 이어질 수
있습니다.

### Q33. 다크모드나 반응형(모바일) 대응은 어느 정도까지 되어 있나요?
현재 스타일 시스템(`theme.css`, `landing.css`)은 라이트 테마 기준의
그라디언트·글래스 색상을 중심으로 설계되어 있고, 히어로의 잭소(퍼즐)
레이아웃도 `sm`/`lg` 브레이크포인트별로 세로 스택 ↔ 가로 3열 배치를
전환하는 등 반응형 자체는 신경 썼습니다. 다만 다크모드 전용 색상
토큰이나 `prefers-color-scheme` 대응 여부는 별도로 확인이 필요한
지점이며, 발표에서 "다크모드 지원 여부"를 물으면 정직하게 "현재는 라이트
테마 우선으로 설계했고 다크모드는 로드맵"이라고 답하는 게 안전합니다.

### Q34. 애니메이션이 많은데(모션, 스크롤 pull, 퍼즐 조각, 신호 반짝임 등)
접근성(모션 민감 사용자)은 어떻게 보장하나요?
`useReducedMotion` 훅을 히어로, 리빌 섹션, 로딩 애니메이션 등 대부분의
모션 지점에서 조건 분기로 사용해 `prefers-reduced-motion: reduce`
사용자에게는 애니메이션을 끄거나 단순화합니다. 다만 이 판단은 전적으로
"애니메이션 유무"에만 적용되어 있고, 스크롤 위치에 따라 레이아웃 자체가
크게 이동하는 히어로 pull 효과처럼 reduced-motion에서도 여전히 존재하는
"큰 시각적 이동" 요소가 완전히 제거되는지, 아니면 이동 폭만 줄어드는
수준인지는 코드로 한 번 더 확인해볼 가치가 있습니다.

### Q35. 디자인 시스템(색상, 타이포, 간격)이 코드 전반에 일관되게
토큰화되어 있나요, 아니면 페이지마다 하드코딩되어 있나요?
`theme.css`에 CSS 커스텀 프로퍼티(`--color-blue`, `--color-ink`,
`--color-slate` 등)로 색상 토큰은 정의돼 있지만, 실제 컴포넌트 곳곳에는
`rgba(255,255,255,0.55)`, `rgba(10,92,255,0.1)`처럼 토큰을 거치지 않은
하드코딩된 색상값도 함께 쓰이고 있습니다. 페이지 수가 아직 적은
프리토타입 단계라 큰 문제는 아니지만, 서비스가 커질수록 이런 하드코딩이
색상 일관성 유지·리브랜딩 비용을 늘릴 수 있다는 점은 스스로 짚고 넘어갈
만한 기술 부채입니다.
