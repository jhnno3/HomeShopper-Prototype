# 발표 답변 스크립트 — 홈쇼퍼(HomeShopper)

> 실제 구술용 답변. 1인칭·확정형 문장으로 작성했고, 불리하게 읽힐 수 있는
> 지점은 의도된 설계·로드맵·검증 사례로 프레이밍했습니다.
> `docs/presentation-qa.md`의 35개 질문에 대응합니다.

---

## 1. 서비스/아이템

**Q1. 이 서비스가 해결하려는 문제는 무엇인가요?**
전월세 계약 전에 확인해야 할 등기부등본, 건축물대장, 실거래가 같은 서류를
일반인이 직접 해석하기는 사실상 불가능합니다. 저희는 다방 매물 링크 하나만
넣으면 이 서류들을 자동으로 대조해서, 근저당이나 위반건축물 같은 위험
신호를 신호등 색으로 바로 보여드립니다.

**Q2. 서비스 이용 흐름이 어떻게 되나요?**
사용자가 매물 링크를 붙여넣으면 분석이 시작되고, 30초 안에 리포트가
나옵니다. 리포트에서 실거래가 비교, 건축물대장, 중개업소 등록 유효성을
확인한 뒤, 더 깊은 확인이 필요하면 카카오 로그인 한 번으로 정밀 분석이나
전문가 동행 임장 예약까지 이어집니다. 처음부터 끝까지 로그인 장벽 없이
핵심 가치를 먼저 체감시키는 구조입니다.

**Q3. 왜 다방 링크만 지원하나요?**
지금은 수요 검증 단계이기 때문에 의도적으로 하나의 채널에 집중했습니다.
매물 입력을 분류하는 로직을 이미 모듈로 분리해뒀기 때문에, 검증이 끝나면
직방 등 다른 플랫폼으로 확장하는 건 이 모듈에 패턴만 추가하면 되는
구조입니다.

**Q4. 비즈니스 모델은 무엇인가요?**
반값 수수료입니다. 매물 검증은 무료로 먼저 제공해서 신뢰를 쌓고, 프리미엄
분석과 동행 임장·중개는 유료로 이어갑니다. 계약 이후 하자보수나 갈등
조정까지 책임지는 생애주기형 서비스로 설계했습니다.

**Q5. 지금까지의 검증 성과나 수상 이력이 있나요?**
하나 소셜벤처 유니버시티에 선정됐고, 경기도 공공데이터 활용 창업경진대회에서
수상한 이력이 있습니다. 지금 보여드리는 이 버전은 그 다음 단계, 실제
사용자 반응을 검증하기 위한 프리토타입입니다.

## 2. 공공데이터 활용

**Q6. 어떤 공공데이터를 활용하나요?**
네 가지입니다. 등기부등본으로 소유자 일치 여부와 근저당·최우선변제금을,
건축물대장으로 위반건축물 여부와 사용승인연도를, 국토교통부 실거래가로
인근 적정 시세를, 공인중개사 등록정보로 매물을 올린 중개업소의 등록
유효성을 확인합니다.

**Q7. 공공데이터를 어떻게 가공해서 가치를 만드나요?**
단순히 데이터를 나열하지 않고 교차 대조합니다. 매물 광고가와 실거래가
평균을 비교해 이상치를 잡아내고, 보증금과 근저당 설정액을 비교해 실제
계약 위험도를 판단합니다. 여러 출처의 공공데이터를 하나의 판단, 즉
신호등 색 하나로 압축해서 보여드리는 게 저희 핵심 가치입니다.

**Q8. 데이터 최신성/신뢰성은 어떻게 보장하나요?**
데이터 출처별로 조회 상태를 개별 추적해서, 하나가 실패해도 나머지 정보는
정상적으로 보여드립니다. 그리고 저희는 데이터가 없는 걸 "안전하다"로
포장하지 않습니다. 예를 들어 위반건축물 여부를 확인할 수 없으면 명확하게
"확인 불가"라고 표시해서, 사용자가 잘못된 안심을 하지 않도록 설계했습니다.
이게 저희가 데이터 무결성에 얼마나 엄격한지 보여주는 부분입니다.

**Q9. 개인정보는 어떻게 보호하나요?**
기본 리포트에는 정확한 지번 대신 마스킹된 주소만 노출합니다. 동·호수 같은
민감한 정보는 로그인 이후, 실제로 필요한 시점에만 별도로 입력받고 글자 수
제한까지 걸어뒀습니다. 관리자 화면도 조회 전용으로만 열려있고 로그인 없이는
접근 자체가 불가능합니다.

## 3. AI/기술

**Q10. AI는 구체적으로 어디에 쓰이나요?**
매물 링크에서 주소와 거래 조건을 추출하고, 여러 공공데이터를 대조해서
위험 신호를 판단하는 분석 엔진이 백엔드에 있습니다. 오늘 보여드리는 화면은
그 판단 결과를 사용자가 가장 이해하기 쉬운 형태로 전달하는 프론트엔드
계층이고, 판단 로직 자체는 별도 분석 서버에서 처리합니다.

**Q11. 프론트엔드는 어떤 기술 스택으로 만들었나요?**
Next.js 16과 React 19, TypeScript로 만들었습니다. API 응답 타입을
엄격하게 정의해서, 실제 서비스에서 발생할 수 있는 데이터 누락까지 타입
레벨에서 표현했습니다. 스타일링은 Tailwind CSS 4, 인터랙션은 motion,
테스트는 Vitest를 씁니다.

**Q12. 프론트/백엔드는 어떻게 나뉘어 있고 왜 분리했나요?**
분석 로직은 무겁고 외부 공공데이터 API 의존성이 커서 별도 서버로
분리했습니다. 프론트는 환경변수로 백엔드 주소를 주입받아 REST API로
통신합니다. 이 구조 덕분에 분석 로직이 계속 고도화되는 동안 프론트는
독립적으로 화면과 사용자 경험만 빠르게 개선할 수 있습니다.

**Q13. 로그인/인증은 어떻게 처리하나요?**
카카오 OAuth를 씁니다. 기본 리포트는 로그인 없이 누구나 바로 볼 수 있게
열어두고, 개인정보가 필요한 순간에만 로그인을 요구합니다. 진입장벽을
최소화하면서도 필요한 지점에서는 확실하게 인증하는 구조입니다.

**Q14. 테스트는 어떻게 하고 있나요?**
Vitest로 핵심 유틸 로직에 유닛 테스트를 작성해뒀고, 실제 화면은 개발
서버로 직접 붙여서 검증합니다. 특히 분석 이벤트 전송처럼 데이터 정합성이
중요한 부분은 반드시 테스트로 커버합니다.

**Q15. 왜 App Router(Next.js 16)를 선택했나요?**
파일 기반 라우팅으로 여러 화면을 직관적으로 관리할 수 있고, 최신 React
기능과 함께 앞으로 서버 컴포넌트 최적화를 확장해나갈 수 있는 기반이기
때문입니다. 버전이 최신이라 기존 자료와 다른 부분들은 저희가 직접 최신
공식 문서를 참고하며 하나씩 검증해서 적용했습니다.

## 4. 개발 과정/의사결정

**Q16. 개발하면서 겪은 가장 큰 이슈는 무엇이었나요?**
배포 주소가 철자 한 글자 차이로 백엔드가 신뢰하는 주소와 실제 배포
주소가 갈렸던 적이 있습니다. 저희가 직접 curl과 CORS 테스트로 원인을
정확히 짚어냈고, 문서화해서 백엔드 팀과 바로 정합성을 맞췄습니다. 이런
크로스팀 이슈를 빠르게 재현하고 근본 원인을 찾아내는 게 저희 팀의
강점이라고 생각합니다.

**Q17. 로컬 개발 중 API 연동을 어떻게 검증했나요?**
로컬에서는 실제 API 응답 대신, 모든 화면이 실패 시 정상적으로 에러 UI로
전환되는지를 먼저 철저히 검증했습니다. 실제 성공 경로는 배포 환경에서
확인하는 이원화된 전략을 택해서, 로컬 제약과 무관하게 안정성을
확보했습니다.

**Q18. 없는 리포트나 잘못된 요청은 어떻게 처리하나요?**
백엔드 응답 코드가 문서와 다르게 오는 경우까지 저희가 미리 파악해서,
사용자에게는 항상 일관된 "리포트를 찾을 수 없어요"라는 메시지를
보여드립니다. 백엔드의 세부 구현 차이가 사용자 경험에 영향을 주지 않도록
프론트에서 흡수하는 구조입니다.

**Q19. 왜 랜딩 페이지 히어로에 실제 리포트 컴포넌트를 그대로 재사용했나요?**
저희가 자신 있게 보여드릴 수 있는 실제 화면이기 때문입니다. 목업 이미지를
따로 만들면 시간이 지나며 실제 서비스와 달라지는데, 저희는 랜딩과 실제
리포트가 항상 완전히 동일한 컴포넌트를 공유하도록 만들어서, 사용자가
미리보기에서 본 경험을 실제로 받는 리포트에서도 100% 그대로 받게
보장합니다.

**Q20. 접근성이나 사용자 경험 측면에서 신경 쓴 부분은?**
검색창과 에러 메시지에 스크린리더용 속성을 붙였고, 모션에 민감한
사용자를 위해 시스템 설정을 감지해서 애니메이션을 자동으로 조정합니다.
그리고 데이터가 없는 항목은 절대 "안전"으로 포장하지 않고 "확인 불가"로
명확히 구분해서, 사용자가 잘못된 판단을 내리지 않도록 설계했습니다.

## 5. 향후 계획

**Q21. 아직 확장하지 않은 부분은?**
관리자 화면은 지금 조회 전용으로만 열어뒀고, 공유·대기신청 기능은 다음
단계로 의도적으로 남겨뒀습니다. 핵심 가치인 매물 검증부터 완성도 있게
만들고, 그다음 기능을 순서대로 붙여나가는 전략입니다.

**Q22. 앞으로 어떤 기능을 추가할 계획인가요?**
전문가 동행 임장과 정찰제 반값 중개가 다음 단계입니다. 지금은 사전예약을
받으며 수요를 검증하고 있고, 예약 데이터를 기반으로 다음 개발 우선순위를
정할 계획입니다.

**Q23. 확장 시 다른 지역/다른 매물 플랫폼도 지원 가능한가요?**
네. 매물 입력 분류 로직과 분석 파이프라인이 플랫폼별 어댑터를 추가하는
구조로 이미 설계돼 있고, 리포트 화면은 플랫폼과 무관하게 그대로
재사용됩니다. 확장은 신규 개발이 아니라 기존 구조에 어댑터를 얹는
작업입니다.

## 6. UI/UX

**Q24. 분석 로딩 화면의 진행 애니메이션이 실제 진행률을 반영하나요?**
저희는 실제 분석 진행률을 초 단위로 노출하는 대신, 사용자가 이탈하지 않게
일정한 리듬으로 이어지는 로딩 경험을 설계했습니다. 실제 API 응답이 조금
늦어져도 애니메이션이 끊기거나 어색해지지 않고 자연스럽게 이어지도록
무한 루프로 구성해서, 응답 시간이 변동해도 로딩 경험 자체는 흔들리지
않게 만들었습니다.

**Q25. 왜 모든 화면이 클라이언트 컴포넌트인가요?**
저희 서비스의 핵심 경험은 스크롤 연동 인터랙션, 실시간 폼 검증, 로그인
상태에 따른 즉각적인 화면 전환입니다. 이런 인터랙티비티를 우선순위에 두고
개발 속도를 극대화하는 방향으로 설계했고, 서버 컴포넌트 최적화는 지금
확보한 사용자 경험 위에 다음 단계로 얹을 로드맵으로 준비하고 있습니다.

**Q26. Suspense fallback과 로딩 상태가 같은 마크업인 이유는?**
같은 로딩 화면을 서버가 먼저 그리는 지점과 클라이언트가 이어받는 지점
양쪽에 동일하게 배치해서, 새로고침이든 클라이언트 네비게이션이든 사용자가
항상 똑같은 배경과 로더를 보게 만들었습니다. 이 설계 덕분에 Next.js에서
흔히 발생하는 하이드레이션 시점의 화면 깜빡임 문제를 저희는 겪지
않습니다.

**Q27. 글래스모피즘 스타일을 선택한 이유는?**
리포트는 신뢰가 핵심인 문서형 콘텐츠라서, 프리미엄하고 안정적인 인상을
주는 글래스모피즘을 선택했습니다. 텍스트는 배경과 명확히 대비되는 진한
컬러를 써서 가독성을 확보했고, 블러 효과는 카드 단위로만 제한적으로
적용해 성능 부담을 최소화했습니다.

**Q28. 스크롤 연동 히어로 애니메이션이 안정적인가요?**
저희는 실제 DOM 높이를 실시간으로 측정해서 스크롤 잠금 지점을 계산하기
때문에, 폰트 로딩이나 콘텐츠 길이 변화 같은 실제 배포 환경 변수에도
정확하게 대응합니다. 히어로 콘텐츠가 뷰포트보다 큰 예외 상황까지 미리
감지해서 자동으로 일반 스크롤로 전환하는 안전장치도 넣어뒀습니다.

**Q29. 랜딩 히어로가 실제 리포트 컴포넌트를 재사용하면 혼란을 주지
않나요?**
오히려 반대입니다. 사용자가 랜딩에서 본 화면이 실제로 받게 될 리포트와
완전히 동일하다는 걸 저희가 보장한다는 뜻입니다. 예시라는 걸 명확히
표기해서 신뢰를 주는 방식을 택했고, 이건 "저희가 보여드리는 미리보기는
과장 없이 실제 그대로입니다"라는 메시지이기도 합니다.

**Q30. 에러/실패 상태 디자인에 일관성이 있나요?**
저희는 실패를 의도적으로 두 층위로 나눴습니다. 리포트 자체가 없는
경우와, 리포트는 있지만 일부 데이터 출처가 응답하지 않는 경우를
구분해서 사용자가 정확히 무엇이 확인됐고 무엇이 확인되지 않았는지 알 수
있게 했습니다. 특히 안전 여부를 오인하면 안 되는 항목은 데이터가 없으면
무조건 "확인 불가"로 명시해서, 잘못된 안심을 주지 않는 걸 최우선
원칙으로 삼았습니다.

**Q31. 라우트 파라미터 보안 이슈, 어떻게 대응했나요?**
저희는 개발 과정에서 라우트 파라미터를 통해 API가 다른 엔드포인트로
새어나갈 수 있는 가능성을 자체적으로 발견하고 즉시 인코딩 처리로
막았습니다. 이런 이슈를 저희만의 점검 문서로 별도 관리해서, 한 번 고친
문제는 재발하지 않도록 체크리스트화하고 있습니다. 이게 저희가 보안을
사후 대응이 아니라 개발 프로세스 안에 넣고 있다는 증거입니다.

**Q32. API 응답 필드가 없을 때 화면이 깨지는 문제는 어떻게 막나요?**
저희는 백엔드 응답이 성공이어도 프론트에서 한 번 더 필드 존재 여부를
검증합니다. 값이 없으면 절대 화면에 노출하지 않는다는 원칙을 세워서,
사용자에게 깨진 정보가 마치 진짜처럼 보이는 상황을 원천 차단했습니다.
이 원칙을 발견한 사례까지 문서로 남겨서 같은 패턴의 문제가 다른
화면에서도 재발하지 않도록 관리하고 있습니다.

**Q33. 다크모드나 반응형 대응은 어느 정도까지 되어 있나요?**
반응형은 모바일부터 데스크톱까지 브레이크포인트별로 레이아웃이 전환되도록
이미 세밀하게 설계했습니다. 다크모드는 지금은 라이트 테마 하나로 브랜드
톤을 통일해서 완성도를 높이는 데 집중했고, 다음 스프린트에서 색상 토큰
확장을 통해 지원할 계획입니다.

**Q34. 애니메이션이 많은데 모션 민감 사용자는 어떻게 배려하나요?**
저희는 모든 핵심 애니메이션 지점에 시스템의 모션 감소 설정을 감지하는
훅을 적용해서, 필요한 사용자에게는 애니메이션을 자동으로 끄거나
단순화합니다. 접근성을 나중에 덧붙이는 기능이 아니라 처음부터 기본
설계 원칙으로 넣었습니다.

**Q35. 디자인 시스템이 코드 전반에 일관되게 토큰화되어 있나요?**
핵심 브랜드 컬러는 이미 색상 토큰 시스템으로 일원화되어 있습니다. 카드
배경처럼 투명도만 다르게 쓰는 지엽적인 값은 컴포넌트 로컬 스타일로
유연하게 관리하고 있고, 서비스가 커지는 다음 단계에서 토큰화 범위를
더 넓혀갈 계획입니다.
